Prerequisites

Checked implicitly, not upfront

!
jq + python3 on PATH
Both required but never checked upfront. Failures surface later as silent no-ops.
no jq Settings.json manipulation fails silently ▶
Without jq, install.sh can't merge the SessionStart hook into an existing settings.json. It falls through to the else branch and overwrites the entire file with a minimal config. If the user had other settings, they're gone.

The statusline mod_taxi() also needs jq to read the timer file. No jq = meter never renders. No error. Just silence.
no python3 Timer file never written ▶
The SessionStart hook uses python3 to write the JSON timer file. Without it, .claude/sessions/{id}.json never gets created. The statusline function checks for the file and returns empty. Meter shows nothing. No error message anywhere.

Project-Level Install

What install.sh actually does — 4 files into .claude/

1
Write hook script
.claude/hooks/taxi-start.sh
Creates the SessionStart hook that writes a timestamp to a per-session JSON file.
# On session start:
mkdir -p .claude/sessions/
# Write {start: epoch, session_id, completions: []}
# On resume: reset start, keep completions
ok Always succeeds if dir is writable
2
Register hook in settings
.claude/settings.json
Adds SessionStart hook entry so Claude Code runs the timer on every session.
if settings.json exists + jq available ▶
Checks if .hooks.SessionStart already has entries. If empty, merges the taxi hook via jq. If hooks already exist, warns and bails — user must add manually. This is the safe path but it's a friction point for projects with existing hooks.
else No settings.json or no jq ▶
Creates a fresh settings.json with only the taxi hook. If settings.json existed but jq is missing, the file gets overwritten — this is a data loss path. The -f check passes, but without jq the script falls through to the else branch.
friction Existing SessionStart hooks ▶
If the project already has SessionStart hooks (common — other tools use them), the installer prints a warning and does nothing. The user must manually edit settings.json to add the taxi hook alongside existing ones. Many users will see the warning, not know what to do, and give up.
3
Statusline config
.claude/statusline.json
Tells the statusline script to render the taxi module for this project.
{"modules": ["taxi"]}
new Creates the file — clean
exists Warns but doesn't merge ▶
If the file already exists (user has other statusline modules), the installer warns but doesn't touch it. User must manually add "taxi" to their modules array. Not destructive, but another manual step.
4
Gitignore sessions
.claude/.gitignore
Keeps per-session timer files out of version control.
sessions/
ok Appends or creates — always safe

Global Setup

Where the install falls apart — two manual steps the user has to figure out

5
Global statusline script
~/.claude/scripts/statusline.sh
The install checks for it. That's all. Three outcomes, two are dead ends.
ok Script exists + has mod_taxi() ▶
User already has the modular statusline with the taxi module function. Everything works. This is only true if they installed taxi-meter before or manually set it up.
friction Script exists but missing mod_taxi() ▶
User has a statusline script but it doesn't have the taxi module function. The installer dumps a ~15-line bash function to the terminal and says "add this." User must:
1. Copy the function from terminal output
2. Open ~/.claude/scripts/statusline.sh
3. Paste it in the right place
4. Hope they didn't break the script

This is where most users bail.
friction No statusline script at all ▶
User has never set up a modular statusline. The installer says "see README.md." User must:
1. Copy statusline.sh from the taxi-meter repo to ~/.claude/scripts/
2. Edit ~/.claude/settings.json to add the statusLine.command setting
3. Restart Claude Code

Two files to create/edit, in a directory they may not know exists. The install printed "success" but nothing will work until they do this.
6
Global settings.json statusLine entry
~/.claude/settings.json
Not checked at all. If this isn't set, the statusline script never runs.
// Required in ~/.claude/settings.json:
"statusLine": {
  "type": "command",
  "command": "~/.claude/scripts/statusline.sh"
}
invisible Never checked — silently required ▶
The installer never checks if the user's global settings.json has the statusLine entry pointing to the script. If it's missing, the statusline script simply never executes. The taxi module exists, the hook runs, the timer file gets written — but nothing reads it. Everything "installed" but nothing displays. No error.

Working State

When everything lands — what actually happens each session

✓
Session lifecycle
# 1. User starts Claude Code
SessionStart hook → taxi-start.sh runs
→ writes .claude/sessions/{session-id}.json

# 2. Statusline polls (every render)
statusline.sh → reads timer → calcs elapsed
→ displays: 🚕 12m30s $31.25 ($150/hr)

# 3. User resumes same session
SessionStart hook → resets start time
→ keeps completions[] intact

# 4. That's it. No stop. No invoice. No export.

Disable & Uninstall

−
Disable for one project
Remove "taxi" from modules or delete the config file.
# Option A: edit the file
# Remove "taxi" from .claude/statusline.json modules array

# Option B: delete it
rm .claude/statusline.json
×
Full uninstall
Remove all taxi-meter files from the project.
rm .claude/hooks/taxi-start.sh
rm .claude/statusline.json
rm -rf .claude/sessions/
# Then remove the SessionStart hook entry
# from .claude/settings.json manually
note settings.json edit is manual ▶
There's no uninstall script. The user has to hand-edit .claude/settings.json to remove the SessionStart hook entry. If they have other hooks, they need to be careful not to break the JSON structure. If they delete the file, they lose all other project settings.
